# Security Release Checklist

Live attacks executed against a running server (PGlite-native engine — real networked Postgres remains BLOCKED, see `docs/PHASE_19_PRODUCTION_OPERATIONS_AND_RELEASE.md` Section D) this phase, plus carried-forward findings from Phases 16–18. Every row is either a real, executed test or explicitly marked NOT APPLICABLE with the reason no attack surface exists.

| ID | Category | Attack | Impact if successful | Evidence | Fix | Status |
|---|---|---|---|---|---|---|
| SEC-19-01 | SQL injection | `' OR '1'='1` injected into the login `email` field | Auth bypass | Zod's `.email()` validation rejected it with 422 before ever reaching Prisma; Prisma's parameterized query builder is used exclusively throughout the codebase (no raw SQL string interpolation exists outside two parameterless `SELECT 1` health-check calls) | None needed | VERIFIED SAFE |
| SEC-19-02 | Oversized payload | 3MB JSON body against a 2MB limit | Resource exhaustion / DoS | Found returning 500 instead of 413; root cause was `error-handler.ts` only recognizing one body-parser error type (`entity.parse.failed`), not `entity.too.large` | Generalized body-parser error mapping by `.type` (`PayloadTooLargeError`, 413); re-verified live | **FIXED** (Phase 19) |
| SEC-19-03 | Malformed JSON | Truncated/invalid JSON body | Information leakage via raw parser error | Fixed in Phase 18 (500→400), re-verified still correct this phase | `MalformedJsonError` (400) | VERIFIED |
| SEC-19-04 | Path traversal | Business Analyzer CSV upload | Arbitrary file read/write via crafted filename | `multer.memoryStorage()` is used — uploaded files are held as in-memory buffers, `file.originalname` is never used to construct a filesystem path anywhere in the codebase | None needed — no attack surface exists | NOT APPLICABLE |
| SEC-19-05 | SSRF | Any endpoint accepting a URL and fetching it server-side | Internal network access, cloud metadata endpoint access | Repository-wide grep for `axios.get/post`, `fetch(`, `http(s).get` outside the OpenAI SDK client found zero matches; the OpenAI client always targets OpenAI's fixed API endpoint, never a user-supplied URL | None needed — no attack surface exists | NOT APPLICABLE |
| SEC-19-06 | Rate limiting | 25 rapid login attempts, same IP | Brute-force credential guessing | First 20 correctly returned 401; requests 21–25 correctly returned 429 with a clean, non-leaking body | `authRateLimit` (pre-existing, re-verified) | VERIFIED |
| SEC-19-07 | CORS | `OPTIONS` request with `Origin: http://evil.example.com` | Cross-origin credential theft | Response's `Access-Control-Allow-Origin` was the fixed configured origin (`http://localhost:5173`), never reflecting the attacker's `Origin` header — a browser would reject reading the response from the evil origin | None needed — `cors()` configured with a static origin string, not a reflecting function | VERIFIED SAFE |
| SEC-19-08 | IDOR / workspace enumeration | Compare "workspace exists, belongs to another tenant" vs "workspace never existed" | Tenant enumeration — an attacker could map which UUIDs are real | Live probe (`backend/src/scripts/security-probe-idor.ts`) proved byte-identical 404 response bodies (aside from `requestId`) for both cases | Pre-existing anti-enumeration design (`NotFoundError` used uniformly, never a distinguishing 403) | VERIFIED |
| SEC-19-09 | Privilege escalation | Mass-assignment of `isSystemAdmin: true` into a registration payload | Self-granted system-admin privileges | Live test: JWT issued after the attempt correctly reflected the real DB value (`false`), not the attacker-supplied one — Zod schemas strip unknown/unlisted fields by default (no `.passthrough()` anywhere) and `req.body` is replaced entirely with the parsed, typed result | None needed | VERIFIED SAFE |
| SEC-19-10 | Privilege escalation | Any endpoint allowing a member to change their own or another member's `roleId` | Self-granted elevated role within a workspace | Repository-wide search found **zero routes that touch `WorkspaceMember` at all** — no invite, no role-change endpoint exists yet | None needed — no attack surface exists (also: this is the same "no invite flow" gap already documented in `docs/FIRST_CUSTOMER_READINESS.md`) | NOT APPLICABLE |
| SEC-19-11 | Tenant isolation | Cross-tenant GET/POST/PATCH/DELETE across contact/lead/business-profile/content-asset/workflow-instance | Cross-tenant data read or write | 13/13 integration tests pass; write-attempt tests additionally re-fetch the target afterward to prove it was left unmodified, not just that the attacking request itself 404'd | `enforceWorkspacePathMatch` middleware (path-vs-token workspaceId check, 404 not 403) | VERIFIED |
| SEC-19-12 | RBAC negative path | VIEWER (0 permissions) attempting a `contact.manage`-gated action; MEMBER attempting `workflow.approve` | Unauthorized privileged action | Both correctly rejected 403 `AUTHZ_INSUFFICIENT_PERMISSION`, response body checked for zero leakage of internal role/permission-set details | `authorize()` middleware (pre-existing, closed this specific test gap in Phase 18) | VERIFIED |
| SEC-19-13 | Secret exposure | Repository-wide scan for `sk-[a-zA-Z0-9]{20,}`, `AKIA[0-9A-Z]{16}` | Committed credentials | Zero matches via `git grep`; only committed env files are `.env.example`/`.env.development`, both containing placeholder/dev-only values | None needed | VERIFIED |
| SEC-19-14 | Error leakage | Every error path this phase and prior phases exercised (401/403/404/409/422/429/500/503) | Stack traces, SQL, internal paths reaching the client | `error-handler.ts`'s unhandled-error branch never serializes `err` into the response, only into server-side `console.error`; re-confirmed for the two new error types added this phase (413, request-timeout 503) | Pre-existing design, extended consistently | VERIFIED |
| SEC-19-15 | Request timeout | No prior ceiling on request duration | A stalled downstream dependency (AI provider, DB) holding a connection open indefinitely | Found as a gap during this phase's production-hardening audit (Section 11) — not an executed attack, a code-review finding | Added `requestTimeout` middleware, 30s default, configurable via `REQUEST_TIMEOUT_MS` | **FIXED** (Phase 19) |

## Summary

15 rows: 3 real bugs found and fixed this phase (SEC-19-02, SEC-19-15, and the malformed-JSON case re-verified from Phase 18), 3 genuinely NOT APPLICABLE (no attack surface exists for path traversal, SSRF, or member-role privilege escalation — confirmed by code search, not assumed), 9 VERIFIED safe or correctly defended through live, executed attacks.

**No Tier-0 failure was found this phase** (no tenant-isolation breach, no credential leak, no unauthorized privileged access succeeded). Per this phase's release-gate rule, a Tier-0 failure would override any numeric score — none exists, so this checklist does not by itself block release; the release verdict is still gated by the real-PostgreSQL and deployment-rehearsal blockers documented in the main Phase 19 record doc, unrelated to security.
